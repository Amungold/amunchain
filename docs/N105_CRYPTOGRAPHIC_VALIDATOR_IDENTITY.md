# N105: Cryptographic Validator Identity

## Overview

The N105 phase replaces the experimental, seed-derived validator identity system with a full cryptographic identity framework. Before N105, the AmunChain consensus layer used hardcoded validator identifiers (such as 1u8 repeated 32 times or 2u8 repeated 32 times) and did not verify cryptographic signatures on votes. Any participant could impersonate a validator by claiming an identifier, because no binding existed between the identifier and a public key, and no signature verification was performed inside the consensus engine.

N105 closes this gap by introducing a new crate, amun-validator-identity, that defines how validator identifiers are derived from Ed25519 public keys. It adds a key registry inside the consensus engine that maps validator identifiers to public keys. It enforces mandatory signature verification on every vote whenever the registry is populated. It integrates with the existing certificate infrastructure in amun-networking to load validator certificates from persistent files, verify them against a test authority, and register the resulting identities in the engine. And it removes all seed-based key derivation from the runtime.

The result is a consensus protocol where votes are authentic, validator identities are cryptographically bound to their keys, and peer discovery relies on verified certificates rather than synthetic seeds.

## Objectives

The phase achieves the following engineering goals. Establish a deterministic, collision-resistant derivation of ValidatorId from an Ed25519 public key using BLAKE3 with a domain separator. Create a registry inside the consensus engine that stores public keys by ValidatorId and resolves PeerId to ValidatorId. Sign every consensus vote with the validator private key and verify the signature before accepting the vote. Load peer identities from certificate files issued by a trusted authority, verifying each certificate before registration. Remove all runtime code that derives keys from hardcoded seeds or validator index numbers. Maintain backward compatibility for consensus-engine unit tests through registry-based activation of signature verification, while requiring certificates for all live-cluster validators.

## Scope

The phase includes the following concrete deliverables. The amun-validator-identity crate containing the ValidatorId type and derivation function, the ValidatorKeyRegistry mapping ValidatorId to public key and PeerId to ValidatorId, and the vote signing payload and Ed25519 verification functions. Modifications to the amun-consensus-network crate where ConsensusEngine gains a validator_keys field of type ValidatorKeyRegistry, along with register_validator and register_validator_identity methods, and signature verification in process_vote that is conditioned on the registry not being empty. Modifications to the amun-live-cluster crate where LiveValidator gains a real Ed25519 signing key, derives its true ValidatorId from the signing key public key, signs outgoing votes with the signing key, loads peer certificates from disk and verifies them against a test authority, and registers them in the engine. Four test certificate files generated once and stored permanently under crates/amun-live-cluster/testdata/certs. Updates to the ClusterPeer struct to carry an optional certificate_path field, and updates to the test cluster constructors to populate certificate paths automatically.

## Architecture

The identity architecture flows from a certificate file to consensus enforcement through a well-defined pipeline. A validator starts with an Ed25519 key pair. The private key is used to sign votes. The public key is embedded in a certificate. The certificate is issued by a trusted authority, which in the test configuration uses the hardcoded seed 0x42 repeated 32 times. The certificate contains the validator PeerId as defined in amun-networking and the public key. The certificate is stored as a JSON file on disk. Each validator in the cluster has its own certificate file.

On startup, the LiveValidator loads the certificate, verifies it against the authority public key, and derives the ValidatorId from the public key using BLAKE3 with the domain separator AMUN_VALIDATOR_ID_V1. The consensus engine ValidatorKeyRegistry maps the derived ValidatorId to the public key. For every vote, the validator signs the canonical payload produced by vote_signing_payload and includes the signature. The receiving engine looks up the public key by the voter_id field, verifies the signature, and rejects votes that fail verification. There is no longer any path to register a validator without a certificate, and no path to accept a vote with an invalid signature.

## Design Principles

Identity is public-key derived. The ValidatorId is a hash of the public key, not an arbitrary number. This prevents identifier spoofing and ensures that the identifier changes only if the key changes. Signature verification is mandatory when the registry is populated. Every vote must carry a valid signature over a well-defined payload. This prevents impersonation and vote forgery. Minimal authority trust. The test setup uses a single hardcoded authority key. The verification logic, however, can be extended to multiple trust anchors without changing the engine internals. No runtime key derivation from seeds. All private key material is generated randomly or loaded from external sources. No deterministic derivation from predictable values exists in the running system. Backward compatibility is achieved via registry emptiness. When the registry is empty, signature verification is skipped. This allows existing unit tests to run unchanged while the production code registers validators.

## Components

The amun-validator-identity crate is a standalone crate providing identity primitives. It has no dependencies on other Amun crates except ed25519-dalek version 2, blake3 version 1, and serde version 1 with the derive feature. Its responsibilities include defining ValidatorId as a 32-byte array, deriving ValidatorId from a 32-byte Ed25519 public key using BLAKE3 with the domain separator AMUN_VALIDATOR_ID_V1, maintaining a bidirectional mapping from ValidatorId to public key and from PeerId to ValidatorId, computing the canonical vote signing payload, and verifying Ed25519 signatures. The public interface includes derive_validator_id which takes a public key and returns a ValidatorId, derive_peer_id which takes a public key and a genesis hash and returns a 32-byte PeerId, ValidatorKeyRegistry with methods new, insert, register_identity, get, len, is_empty, and get_validator_id_from_peer, and the free functions vote_signing_payload and verify_ed25519.

The ConsensusEngine in amun-consensus-network is modified to store a ValidatorKeyRegistry alongside existing consensus state. It provides register_validator and register_validator_identity for populating the registry. In process_vote, if the registry is non-empty, it enforces signature verification before any other checks. Votes from unknown validators or with invalid signatures are rejected. The public interface adds the validator_keys field of type ValidatorKeyRegistry, the register_validator method taking a validator_id and a public_key, and the register_validator_identity method taking a peer_id, a validator_id, and a public_key. The data flow is as follows. When a vote arrives, process_vote checks if the validator_keys registry is empty. If it is not empty, the method looks up the voter public key via validator_keys.get, computes the signing payload using vote_signing_payload, verifies the signature with verify_ed25519, returns an error if any step fails, and then proceeds with the usual height, round, and equivocation checks.

The LiveValidator in amun-live-cluster is modified to generate a fresh Ed25519 signing key on startup, derive its ValidatorId and PeerId from that key, sign every vote it produces with the signing key, load peer certificates from files and verify them, and register them in the engine. It no longer derives peer keys from seeds. The public interface includes a signing_key field of type SigningKey and a validator_id field that holds the cryptographic identifier. The new constructor now registers self and peers via certificates.

The data flow inside LiveValidator proceeds as follows. Generate a random SigningKey. Compute the public key from the signing key verifying key. Compute the validator_id by calling derive_validator_id on the public key. Load the self certificate if it exists. For each peer in the config cluster, load its certificate from the path, verify it with the authority key, extract the public_key field, derive the validator_id, and call engine.register_validator_identity. In the consensus thread, when creating a vote, compute the timestamp, build the payload with vote_signing_payload, sign with the signing key, and set the signature field to the resulting 64-byte signature.

The Config and ClusterPeer types in amun-live-cluster are updated. ClusterPeer gains a certificate_path field of type Option string with the serde default attribute so that existing code that constructs ClusterPeer literals can omit the field and receive None. A free function set_cert_paths populates the field from the crate testdata certs directory using the CARGO_MANIFEST_DIR environment variable. The localhost_cluster and test_cluster constructors call set_cert_paths after building the cluster vector. The benchmark binaries benchmark_10.rs and benchmark_10_event.rs are updated to include certificate_path: None in their ClusterPeer literals.

Four certificate files are stored under crates/amun-live-cluster/testdata/certs. These are validator_1.crt through validator_4.crt. Each is a JSON serialization of a ValidatorCertificate issued by the test authority with seed 0x42. The subject of each certificate is the validator PeerId derived from a deterministic seed, one per index. The public key is derived from that same seed. The certificates are generated once and committed to the repository.

## State Management

The ValidatorKeyRegistry is not persisted to disk in this phase. It is rebuilt on every startup by reloading certificates. The registry is populated before any consensus activity begins. Once populated, it remains immutable for the lifetime of the process. Validators are not added or removed dynamically in the test clusters. The consensus engine validator_id field is set to the cryptographic ValidatorId of the local node, replacing the old configuration-based identifier.

## Consensus Impact

Vote acceptance now requires that votes from registered validators carry a valid signature. Unsigned or incorrectly signed votes are rejected with an error. Quorum counting is unchanged and uses the same active_validator_count logic, now operating over the registered validator identifiers. Proposer selection is unchanged and still uses round-robin selection over the registered identifiers. Equivocation detection remains functional, as it compares voter_id and block hashes. Signature validation adds an additional layer of evidence, because an equivocating validator must still sign both conflicting votes, making the proof of misbehavior cryptographically stronger. The performance impact is one Ed25519 verification per vote, which is a constant-time operation taking microseconds. There is no measurable impact on consensus throughput in test clusters.

## Security Considerations

Vote forgery resistance is achieved because without the private key, an attacker cannot produce a valid signature for a given voter_id. The registry ensures that only known validators can attempt to vote. Sybil resistance is enforced because the registry is populated from certificates signed by the authority. An attacker cannot inject fake validators. In a production setting, the authority would be the genesis trust anchor set. Replay protection is provided by the signing payload, which includes the height, block hash, and timestamp, binding each vote to a specific consensus round. The authority key is currently hardcoded to the seed 0x42, which is acceptable for test clusters. In production, this key must be distributed via genesis configuration and protected. Certificate integrity is verified at load time. A tampered certificate will cause a panic in test clusters or an error in production loading code, preventing the node from participating.

## Failure Scenarios

If a certificate file is missing, the expect calls in validator.rs will panic, preventing the node from starting. This ensures immediate detection of misconfiguration. If a certificate has an invalid signature, the node panics on startup, preventing participation in consensus with a forged identity. If a certificate file is corrupted, the serde_json from_str call will fail with a descriptive error message. If the registry is not populated due to a bug, signature verification is skipped because the legacy mode is active when the registry is empty. In N105.5D the live cluster always populates the registry from mandatory certificate files before consensus starts. This is safe but should not occur in normal operation because set_cert_paths is always called in the test constructors. The case of a peer providing a wrong key at runtime is not applicable because keys are loaded from local certificate files, not from network handshakes. Network identity exchange is handled by a separate layer.

## Performance Characteristics

Key derivation uses a BLAKE3 hash of 32 bytes, which is negligible. Signature verification performs one Ed25519 verification per vote. Ed25519 verification is fast, on the order of microseconds. For a cluster of four nodes, the overhead is unmeasurable. Certificate loading occurs once at startup. Each file is a few hundred bytes of JSON. There is no impact on steady-state consensus throughput. The ValidatorKeyRegistry stores a small BTreeMap with four entries in test clusters, using negligible memory.

## Testing Strategy

Unit tests for amun-consensus-network include 31 tests covering the original consensus scenarios as well as the new N105 signature enforcement test. The test n105_signature_required_when_registry_populated explicitly validates that a correctly signed vote is accepted and an unsigned vote is rejected when the registry is populated. Integration tests for amun-live-cluster include 7 live cluster tests that exercise multi-validator consensus with the full certificate pipeline. These tests pass because the cluster constructors automatically set certificate paths. The full workspace test suite runs hundreds of tests across all crates, all of which pass without modification. This verifies that the structural changes, including the new field in ClusterPeer and the new crate, do not break any other component. Manual verification confirms that seed-based derivation no longer appears in the live cluster source code.

## Compatibility

Backward compatibility is preserved because all existing tests pass without changes. Signature enforcement is conditional on the registry being non-empty, and test clusters populate the registry via set_cert_paths, so they exercise the new code path. Source code constructing ClusterPeer literals must include the field, while serialized configurations remain backward compatible through serde default handling. All known construction sites were updated as part of this phase. Forward compatibility is designed into the registry and certificate loading infrastructure, which can be extended to support multiple trust anchors, certificate revocation, and network handshake-based key discovery without altering the engine vote processing logic. Serialization compatibility is maintained because ClusterPeer uses the serde default attribute for the new field, so existing serialized configurations remain readable if they exist.

## Operational Notes

The test certificates in testdata/certs are generated once and committed to the repository. They can be regenerated using the gen_test_certs binary if the certificate format changes. The authority seed 0x42 is hardcoded in multiple places. In a production deployment, this must be replaced with a configurable genesis authority key. The certificate_path field in ClusterPeer is optional at the type level for backward compatibility but required by the LiveValidator runtime. The test constructors always set it.

## Limitations

The trust anchor is a single hardcoded test key. There is no support for multiple authorities or key rotation. Certificates are stored as local files. There is no network-based certificate distribution or peer-to-peer authentication in this phase. The ValidatorKeyRegistry is rebuilt from scratch on every restart without persistence. There is no mechanism for dynamically adding or removing validators at runtime.

## Future Extensions

Replace the hardcoded authority with genesis trust anchors loaded from a configuration file. Implement certificate expiry and renewal. Add network handshake authentication where peers present their certificates and prove possession of the corresponding private key. Persist the ValidatorKeyRegistry to disk and support incremental updates. Support threshold signature aggregation for quorum certificates.

## Acceptance Criteria

The amun-validator-identity crate exists with all specified types and functions, and its own three unit tests pass. The ConsensusEngine has a validator_keys field, and process_vote enforces signature verification when the registry is non-empty. The test n105_signature_required_when_registry_populated passes. The LiveValidator generates a real signing key, derives its ValidatorId, signs votes, and loads peer certificates from files. No seed-based derivation or SigningKey from_bytes calls exist in the live cluster runtime source. No runtime fallback path exists for validator identity registration. Certificates are mandatory for all live-cluster peers. All four certificate files exist in the testdata certs directory. The full workspace builds without warnings related to N105. All existing workspace tests pass.

## Conclusion

N105 transforms the AmunChain consensus layer from a prototype with dummy identifiers and no authentication into a system with cryptographically verifiable validator identities and signature-enforced voting. The implementation integrates cleanly with the existing certificate infrastructure, introduces a new reusable identity crate, and removes all legacy seed-based derivation. The workspace is stable, all tests pass, and the foundation is ready for production-grade trust anchor management and network identity verification in subsequent phases.
